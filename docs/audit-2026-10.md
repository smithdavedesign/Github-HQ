## TL;DR

**The code is in better shape than the system.** Typecheck, lint (0 warnings), knip and 1,057/1,057 unit tests are all clean, and the factory has shipped 4 merged PRs at $0. The running system has been degraded for about 7 weeks without anything noticing:

1. **Every scheduled job except one stopped on Aug 14.** GitHub disabled all five `cron-*.yml` workflows for inactivity (`disabled_inactivity`) after 60 days without a commit. Since then there has been no scheduled sync, health snapshot, security scan, uptime check, AI summary or Monday digest/auto-dispatch. The trend chart still says "warming up", Deployments shows "last checked 1mo ago", and the Security page reflects August.
2. **The one cron still running has failed every day since June.** `gstack-self` (Vercel cron) matches a deleted repo, `smithdavedesign/RepoHQ`, that sync never pruned. Every clone fails. That accounts for most of the **487 failed / 2 merged** shown on `/agent-performance` and 127 `agent_execution_failed` events in the last 30 days.
3. **Production runs framework versions with critical advisories.** `next@16.2.6` (fixed in 16.4.0) and `next-auth@5.0.0-beta.31` (fixed in beta.32) are semver-compatible upgrades. `npm audit`: 33 advisories (5 critical, 18 high). Dependabot is off on all 9 repos and CI has no audit gate, so they accumulated quietly.
4. **The two agent executors have very different results.** Nexus: 306 queued → 29 PRs → 2 merged (<1%). Factory: 24 attempts → 12 verified → 4 merged, 2 rejected, $0. The project has two ways to do one job, and only one of them works.
5. **The scoring tells a story nobody can act on.** 51 of 66 repos are "Dead" (mostly archived coursework), average health is 51, and no repo reaches the "high opportunity" threshold (max 31 vs 50), so the Opportunity × Effort matrix puts all 66 in "Deprioritize".

**Verdict:** the dashboard does what it set out to do when its data is fresh, and the factory is the best part of the system. What's missing is *operational truth*: when a pipeline dies, nothing says so. Fix the five items above before building anything new.

## 3. Security review

**What's solid**
- Every protected page redirects logged-out users to `/login`. The guard is layered: `proxy.ts`, plus `(app)/layout.tsx` checking `session?.user?.id`.
- Every API route checks something:
  - user routes check the session;
  - cron routes check the bearer secret, fail-secure when unset;
  - the Nexus webhook uses a constant-time secret;
  - the Stripe webhook verifies the HMAC with 5-minute replay protection.
- Server actions reachable from the client re-check the session and scope by `userId`, for example `queueAdvisorAction` and `queueGstackSkill` verify repo ownership.
- GitHub tokens and LLM keys are encrypted at rest (AES-256-GCM, Phase 58).
- Headers: HSTS preload, nosniff, `X-Frame-Options: SAMEORIGIN`, referrer and permissions policies.
- MCP is stdio-only and scoped to one `MCP_USER_ID`.
- Nexus internal routes use hashed, scoped service tokens.
- Factory: Docker sandbox, egress allowlist, model-alias relay, judge guard on its own code, $0 at night.

**What to fix**: items 1, 6, 7, 10, 11 and 13 above. Also:
- **`proxy.ts` matcher covers only 6 prefixes.** `/`, `/agent-performance` and `/repos/*` rely on the layout guard alone. That works, but the one Auth.js advisory about existence-based checks failing open is exactly the `!session` pattern `proxy.ts` uses. Check `session?.user?.id` there too, and match everything except `/login`, `/pricing`, `/u/*`, `/api/*` and static assets.
- **Nexus has 18 production advisories** (1 critical `proxy-addr`; high: `fastify` host spoofing, `fast-xml-parser`, `path-to-regexp`). Run the same upgrade pass there.
- **LiteLLM key `sk-local-ai` is a guessable constant that also reaches paid `cloud-smart`.** The sandbox relay mitigates it for the factory. The Anthropic console spend cap (Phase 60, owner action) is still the only hard limit for everything else on the machine.

## 4. Architecture

```
RepoHQ (Vercel, Next 16, Neon) ── dashboard, scoring, advisor, dispatch UI
   ├─ GitHub Actions crons ──► /api/cron/*        ← disabled since Aug 14
   ├─ Vercel cron ──► /api/cron/gstack-self ──► Nexus   ← fails daily (deleted repo)
   └─ "Run agent" ──► Nexus (Render: Fastify + BullMQ + Redis + Postgres + MinIO, 27.7k LOC)
                         └─ gstack skills on a cloud worker → PRs   (2 merged / 306 queued)

Factory (Mac, launchd, 4.4k LOC) ── sense → rank → sandboxed build → judge → draft PR
   └─ LiteLLM :4000 free pool (Ollama / OpenRouter / Gemini) → 4 merged / 24 attempts, $0
   └─ writes agent_attempt / agent_jobs back to RepoHQ's Neon DB
```

**What's good**
- Clean server/client split.
- Pure, well-tested scoring and routing modules.
- The factory is a disciplined loop: deterministic checks first, then an adversarial reviewer, a capability ladder, and an append-only ledger that's the source of truth.
- Release governance (`integration/agent` → labelled release to `main`) works in both repos.

**Structural concerns**
1. **Two executors.** Nexus and the factory both take "a task on a repo" to "a PR". Nexus is 6× larger, needs a paid always-on Render stack plus Redis and MinIO, and has a <1% success rate. The factory is smaller, sandboxed, judged and measured. Every Nexus feature (auto-dispatch, gstack-self, the auto-chain, CI-fix queue) adds failure volume without adding merges.
2. **Scheduling depends on repo activity.** GitHub disables scheduled workflows in public repos after 60 days without a commit, and the roadmap's "Infrastructure" table calls those workflows canonical. Now that the factory and releases commit regularly this is less likely, but the system needs to detect it (watchdog, item 2) rather than assume it.
3. **No reconciliation with GitHub.** Sync upserts by `github_id` and never removes anything. Deleted repos linger forever, and they show up in counts, the public profile and agent targets.
4. **Large action files.** `actions/repositories.ts` (1,022 lines, 35 actions) and `actions/nexus.ts` (713) mix UI actions, cron entry points and internal helpers. Splitting them by caller (UI action vs cron/internal) also fixes item 7.

## 9. Worth discussing

1. **One executor.** *Decided 2026-10-06: yes; see [agent-hq-migration-prd.md](agent-hq-migration-prd.md) (roadmap Phase 81).* Make the factory the only path that writes code. RepoHQ's "Run agent", auto-dispatch and the CI-fix queue would enqueue into the factory's owner-request queue (the #17 front door already exists), and Nexus would be frozen at report-only or retired. That saves the Render bill and removes most of the failure noise, and every PR would go through one sandbox and one judge. The alternative is to keep Nexus, but then it needs the same judge and sandbox, and a success target it has to meet before any scheduled triggers run.
2. **Personal tool or product?** There's one inactive second account (41 repos, none synced since June), a pricing page, Stripe wiring and a Distribution roadmap. If it's a personal tool: delete pricing/Stripe/multi-tenant scaffolding and optimise the public profile as a portfolio. If it's a product, D1 (GitHub App) and D2 (isolation) come before any new feature.
3. **Feature depth over breadth.** The June review's point still holds. Advisor, Goals, CEO Report, Simulation and Valuation are unused (empty states, $5 MRR across the portfolio). Consider hiding unused cards behind a "More insights" section until they're used, and spend the effort on the three things that are used: health, triage and the factory.
4. **Observability for a mostly unattended system.** Both outages in this audit (crons and gstack-self) ran for weeks unnoticed. The morning report is the natural place for the check: data freshness, cron last-run, Nexus success rate and stale PRs, plus one red line when any of them is off.
